## 5. CRONJOB BRIDGE — ❌ BROKEN (root cause identified)

**Job:** `Hermes → Zeg Live Bridge` (id `a15ead6675cf`)
- `enabled: True`, `schedule: every 1m (60s)` ✅ (correct cadence)
- `no_agent: True` ✅
- **`script` field = a 1742-char inline bash body** starting with `#!/bin/bash…`
- `last_error`: `Script execution failed: [Errno 63] File name too long: '/Users/neosteinhoff/.hermes/scripts/#!/bin/bash\n# Hermes → Zeg real-time bridge watcher\n…'`
- `/tmp/zeg_last_seen.txt` **never created** (bridge never successfully ran).
- **Cron incident `a15ead_41af198b7849` is OPEN / unacked** (`state:'detected'`,
  `closed_at: null`), failing continuously since 2026-08-29 14:58, last seen 15:25.

### Root cause
Hermes's cron executor (`cron/scheduler.py:_run_job_script`, ~line 4272) treats the
job `script` field as a **filepath** relative to `~/.hermes/scripts/`. It does
`Path(script_path).expanduser().resolve()` and runs `subprocess.Popen([...script_path])`.
Because the bridge job stored an **inline script body instead of a file path**, the
entire 1742-char bash source is passed as a filename → `OSError: [Errno 63] File name
too long`. The job design (poll 8502, POST webhook to 8700) is correct; only the
*delivery mechanism* is wrong.

### Fix (one of):
1. **Write the script to a file** and set `script` to its path, e.g.
   `~/.hermes/scripts/zeg-bridge.sh`, then update the cron job's `script` field to
   `/Users/neosteinhoff/.hermes/scripts/zeg-bridge.sh`. (Hermes restricts `script` to
   `~/.hermes/scripts/` — an absolute path inside that dir is allowed.)
2. Or convert the bridge to a **regular LLM-free `no_agent` job driven by the scheduler's
   own HTTP calls** (the script's logic is just curl — could also be replaced by a
   Python monitor script under `scripts/`).

Until fixed, **The Zeg dashboard will not receive automatic Hermes-CC events** — the
real-time feed only populates via manual webhook POSTs. The webhook/SSE plumbing
itself is healthy; it is starved of input.
